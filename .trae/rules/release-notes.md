# 发版必须附带更新说明

每次发版（打 tag + 触发 `Build and Publish App`）都必须先写好本版本的更新说明文件，release 正文由工作流自动读取，不再手写、不再事后补。

## 文件位置与命名

- 目录：仓库根目录 `release-notes/`
- 文件名：`release-notes/<版本号>.md`，例如 `release-notes/50.0.6.8.md`
- 版本号与 `core/version.py` 的 `CURRENT_VERSION`、release tag 完全一致（tag 可带 `v` 前缀，文件名不带）
- 一个版本一个文件，发布后保留，不覆盖、不删除
- 新规则从下一版开始适用；已发布的说明文件（如 `release-notes/50.0.6.7.md`、`50.0.6.8.md`）按当时格式保持原样，不回改，也不作为新格式的样板

## 写作格式

- 三个二级标题，顺序固定：`### 修复`、`### 新增`、`### 移除`；某段没有内容就整段省略（连标题一起删）
- 一条一个改动、一句话、句号结尾；不把多件事合并进一条，不写「若干问题」「多项优化」这类概括，不复述技术原因
- 每条直接写用户能感知到的结果；修复类直接写「现在怎样」，不必每条都交代「之前怎样」
- 一条改动只影响某个平台时，在句子里点明（例如「手机上…」），不为平台单独开段
- 内容范围严格是上一个发布 tag 到本版 tag 之间的改动，不是"这一轮的改动"，也不是凭记忆写：
  - 写之前先跑 `git log <上一个tag>..<本版tag> --oneline`，把提交全部过一遍
  - 每条归入修复 / 新增 / 移除；纯内部重构、文档、CI 类不面向用户，可以不进正文，但要逐条确认过它确实与用户无关
  - 不许漏：确认每条提交都有去处（进正文，或被明确判定为不面向用户）
- 结尾给一句升级说明（例如「直接安装覆盖即可；Android 与桌面端可以分别更新」）
- 面向用户的话：用「频道列表不再跳回顶部」，不用「修复 NestedScrollView 越界回弹」

## 示例模板

下面是按 `50.0.6.7..50.0.6.8` 的真实改动写成的示例，可直接照抄结构；示例里的条目就是要写进正文的内容本身，不是写法说明。

```markdown
### 修复

- 电视和盒子上 4K 播放的卡顿和黑屏减少，起播失败会自动换一条播放路径。
- 遥控器在播放页选播放方式时，焦点框不再错位。
- 全屏和横屏下打开底栏样式弹窗，手指点选不再被误关。
- 信息弹窗的 EPG 来源不再显示「未知源」。
- 切到没有节目单的频道时，不再显示上一个频道的节目。
- 同名频道带上分辨率后缀，1080P 与 576P 能分清。

### 新增

- 信息弹窗新增 EPG 来源、频道名、ID 与匹配方式。
- 媒体信息里能看到色彩模式、输出范围、是否 HDR 直通等诊断信息。
- 设置里新增「色彩兼容模式」开关，个别设备过曝或发灰时可尝试。

直接安装覆盖即可；Android 与桌面端可以分别更新。
```

没有内容的段落直接整段删掉，包括标题；`### 新增`、`### 移除` 常常整段不出现。本版没有移除项，所以示例里就没有 `### 移除` 段；最后一行的升级说明每次都要保留。

## 禁止内容

- 不贴 commit hash、PR 编号、分支名
- 不提内部文件名、类名、函数名、配置键
- 不写「测试通过」「CI 全绿」这类内部流程结论；设备实测结论可以用用户能理解的话表述
- 不按平台分段，不为同一改动在多段重复
- 不留空正文、不留「待补充」占位，也不要用空话凑字数

## 工作流保障

- `.github/workflows/build.yml` 的 `validate-version` 作业会检查 `release-notes/<版本>.md`
- 文件缺失、或去掉空白与标题后有效字符少于 200 个，直接失败，所有平台作业都不会开始，不会产出空正文的 release
- 条目确实少时，把每条的具体表现写清楚，不要用空话凑字数
- 各平台作业用 `body_path` 写入同一份说明作为 release 正文
